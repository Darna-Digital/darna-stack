---
title: Local dev
description: Install, fill in two env files, run pnpm dev.
---

`pnpm dev` runs all three apps at once. The backend runs under `alchemy dev`,
which provisions its Cloudflare resources (Worker, Hyperdrive, R2, the
PlanetScale database) and then serves the Worker locally against them. The
Next.js apps run under `next dev`.

## Prerequisites

- Node 22+ and pnpm 10+.
- Cloudflare and PlanetScale credentials available to Alchemy — it provisions
  real resources on first run. See the [Alchemy docs](https://alchemy.run) for
  how it picks up credentials.

## Setup

<Steps>

<Step>

### Install

```bash
pnpm install
```

One lockfile, at the repo root. If you find a stray `pnpm-lock.yaml` inside an
`apps/<app>/` directory, delete it — `create-next-app` writes one before it
realises it's in a workspace, and OpenNext stops at the first lockfile it
finds.

</Step>

<Step>

### Backend env

Create `apps/backend/.env`:

```bash
BETTER_AUTH_URL=http://localhost:1337      # must match the alchemy dev worker URL
WEB_CLIENT_URL=http://localhost:7001       # CORS + trusted origin for auth
BETTER_AUTH_SECRET=...                      # any random string for local dev

# Optional — tracing is off unless both are set
OTEL_EXPORTER_OTLP_ENDPOINT=
GRAFANA_OTEL_AUTH_HEADER=
```

The database connection comes from the Hyperdrive binding Alchemy sets up, so
there's no `DATABASE_URL` to manage here.

</Step>

<Step>

### Web client env

Create `apps/web-client/.env.local`:

```bash
NEXT_PUBLIC_API_URL=http://localhost:1337
```

This points the typed API client and the auth client at the local backend.
(It defaults to `:4000` in code, which is wrong for this stack — set it.)

</Step>

<Step>

### Run

```bash
pnpm dev
```

| App              | URL                                 |
| ---------------- | ----------------------------------- |
| Backend          | http://localhost:1337               |
| Web client       | http://localhost:7001               |
| Docs (this site) | http://localhost:3001               |
| OpenAPI spec     | http://localhost:1337/openapi.json  |
| API reference    | http://localhost:1337/docs (Scalar) |

</Step>

</Steps>

## Per-app commands

```bash
pnpm dev:backend     # alchemy dev   (:1337)
pnpm dev:web-client  # next dev      (:7001)
pnpm dev:docs        # next dev      (:3001)
```

`pnpm dev:backend` runs the real Workers runtime under Miniflare with the same
bindings it gets in production, so there's no "works in dev, breaks on deploy"
gap.

## Database migrations

Edit `apps/backend/src/layers/db/schema.ts`, then run `alchemy dev` (or
`deploy`). Alchemy's Drizzle integration generates the SQL into
`src/layers/db/migrations/` and the PlanetScale branch applies it. There's no
separate migrate step to run by hand.

## Regenerating the typed client

After you change a backend route, refresh the web client's types:

```bash
pnpm dev:backend                       # one terminal
pnpm --filter web-client gen:api       # another
```

`gen:api` reads `http://localhost:1337/openapi.json` and writes
`apps/web-client/lib/api-schema.d.ts`. See [Web client](/docs/web-client).

## Working against the deployed backend

To run the web client against the edge backend instead of a local one,
`pnpm --filter @darna/backend dev:remote` redeploys the Worker on every save;
point `NEXT_PUBLIC_API_URL` at its `*.workers.dev` URL.

## Common stumbles

**Auth 401s / cookie not sticking** — `BETTER_AUTH_URL` must match the URL the
worker is actually served on, and `WEB_CLIENT_URL` must be the origin the
browser loads from. A mismatch breaks CORS or the cookie's SameSite rules.

**Web client can't reach the API** — check `NEXT_PUBLIC_API_URL`. The in-code
default is `:4000`, but the backend runs on `:1337`.

**Port 1337 already in use** — usually a stale `alchemy dev`. Kill it and retry.
