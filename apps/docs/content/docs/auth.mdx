title: Auth
description: better-auth runs inside the backend. Email/password, cookie sessions, verified by a middleware.
---

Auth is [better-auth](https://better-auth.com), mounted inside the backend at
`/api/auth/*`. There's no external identity provider. The web client signs in
through better-auth's React client; the session is a cookie; protected API
groups verify it with an Effect middleware.

## The pieces

| Concern              | Where                                                                |
| -------------------- | -------------------------------------------------------------------- |
| Auth instance        | `features/auth/better-auth.ts` — `makeAuth(...)`                     |
| Auth routes          | `/api/auth/*`, handled in `worker.ts`                                |
| Session lookup       | `/api/me` returns the current user or `null`                         |
| Route protection     | `features/auth/auth.middleware.ts` + `.live.ts`                      |
| Web client           | `apps/web-client/lib/auth-client.ts` — `createAuthClient`            |

## How it works

better-auth owns sign-up, sign-in, email verification, and password reset.
`makeAuth` configures email/password with a Drizzle adapter over the same
Postgres pool (the `user`, `session`, `account`, `verification` tables), and
sends verification and reset emails through the backend's email layer:

```ts
return betterAuth({
  baseURL: cfg.baseURL,
  basePath: "/api/auth",
  trustedOrigins: [cfg.webClientUrl],
  database: drizzleAdapter(db, { provider: "pg", schema: authSchema }),
  emailAndPassword: { enabled: true, sendResetPassword: /* … */ },
  emailVerification: { sendOnSignUp: true, sendVerificationEmail: /* … */ },
  advanced: { /* cookie SameSite/secure, optional cross-subdomain */ },
});
```

The browser calls these through the web client's auth client, which talks to
the backend with `credentials: "include"` so the session cookie is set and sent
cross-origin:

```ts
// apps/web-client/lib/auth-client.ts
export const authClient = createAuthClient({
  baseURL,                                  // → appends /api/auth
  fetchOptions: { credentials: "include" },
});
export const { signIn, signUp, signOut, useSession } = authClient;
```

## Protecting a route

A group opts in with `.middleware(Authentication)`. The middleware is declared
as an `HttpApiMiddleware` whose security is the `better-auth.session_token`
cookie, and which provides a `CurrentUser` to handlers:

```ts
// features/auth/auth.middleware.ts
export class Authentication extends HttpApiMiddleware.Service<
  Authentication,
  { provides: CurrentUser }
>()("Authentication", {
  error: NotAuthenticated,                  // → 401
  security: { cookie: HttpApiSecurity.apiKey({ in: "cookie", key: "better-auth.session_token" }) },
}) {}
```

The live implementation resolves the cookie into a user via
`auth.api.getSession(...)`, failing with a 401 when there's no valid session:

```ts
// features/auth/auth.middleware.live.ts
export const AuthenticationLive = Layer.succeed(Authentication, {
  cookie: (httpEffect, { credential }) =>
    resolveUser(credential).pipe(
      Effect.flatMap((user) => Effect.provideService(httpEffect, CurrentUser, user)),
    ),
});
```

Inside any handler in a protected group, read the user with `yield* CurrentUser`.

## Cross-domain cookies

In production the web client and backend sit on different subdomains, so the
session cookie has to cross domains. `makeAuth` switches cookie attributes based
on the backend URL: `SameSite=None; Secure; Partitioned` over HTTPS, plus
optional `crossSubDomainCookies` when `AUTH_COOKIE_DOMAIN` is set. Locally
(plain HTTP) it falls back to `SameSite=Lax`.

<Callout type="info">
  Locally, `BETTER_AUTH_URL` must match the URL the worker is served on and
  `WEB_CLIENT_URL` must be the browser's origin. If they drift, the cookie won't
  stick and every protected call returns 401.
</Callout>
